# M0/M1 — implementation scope

## M0 — specification freeze

Frozen decisions:

1. Intervals.icu is the upstream training/wellness source.
2. The app is the source of truth for coaching decisions, not raw training data.
3. One physical workout can have multiple source recordings.
4. `canonical_session` represents one physical workout.
5. Metrics in a canonical session may come from different source recordings.
6. Every selected metric must preserve provenance.
7. Duplicate auto-merge is conservative and reversible.
8. Webhooks will later accelerate sync, but periodic reconciliation remains mandatory.
9. AI does not participate in duplicate detection in M1.
10. All writes must be idempotent.

## M1 — foundation

### Included

- monorepo layout,
- PostgreSQL schema,
- Alembic migration,
- FastAPI shell,
- minimal athlete bootstrap endpoint for private development,
- Intervals API client using personal API key via HTTP Basic Auth,
- activity normalization,
- idempotent source activity upsert,
- deterministic duplicate engine,
- canonical session builder,
- metric provenance,
- sync endpoint,
- tests for duplicate scoring and field-level merge,
- PWA/Next.js shell.

### Not included yet

- public authentication,
- Intervals OAuth,
- webhooks,
- wellness sync,
- plan domain,
- session pairing to planned workouts,
- AI Coach,
- push notifications.

## Vertical slice acceptance criteria

Given two Intervals activities that represent the same indoor ride:

- Garmin contains power + HR + cadence but no distance,
- MyWhoosh contains power + cadence + distance but no HR,

then the application must:

1. detect them as a probable duplicate,
2. create one canonical session,
3. count it once,
4. use Garmin HR,
5. use MyWhoosh distance,
6. store provenance for both metrics,
7. keep both original source records unchanged,
8. produce the same database result when sync is retried.
